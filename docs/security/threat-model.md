# Threat model

What Setu protects, from whom, and where each protection lives. Update this file in the same pull request as any change that adds a way in (a new IPC command, a new file Setu reads, a new network call) or changes one of the protections below.

## What we protect

| Asset | Where it lives | Protection |
|---|---|---|
| SSH passwords and key passphrases | `vault.json` | Argon2id (64 MiB, 3 passes) + XChaCha20-Poly1305; header authenticated as AAD; file 0600, written atomically; secrets zeroized in memory; auto-lock |
| Vault unlock key ("unlock automatically") | OS keychain (opt-in) | Only the derived key, never the password; deleted when it stops matching |
| Private keys | `~/.ssh` | Made 0600, never overwritten; passphrases never on a command line |
| Trust in servers | `~/.ssh/known_hosts` | Strict checking; changed keys refused with a warning; only keys a server actually offered can be trusted; host names that would be patterns are refused |
| Files being edited | per-user private folder | 0700 random folder under `XDG_RUNTIME_DIR` or `~/.cache` (Linux), per-user temp elsewhere; deleted on close, swept after a week |
| What you type and see | memory only | Never logged; `session.json` holds hosts, users, ports and key paths only |
| Workflows and their run output | `workflows/*.toml`, `workflow-runs.json` | 0600 files (folder 0700), written atomically; history keeps the last 100 runs and 8 KiB of output per host; **Clear run history** removes it |
| Task board cards (titles, notes, host names) | `board.toml` | 0600 file, written atomically; size-capped and checked (ids, lengths, dates) on load and on save; a file that fails to load is never written over; cards never run anything |
| Commands you ran (work memory, opt-in) | `work-memory.json` | Off until turned on; nothing typed at a password/PIN/token prompt or without echo is kept; secrets masked before saving (`setu-memory::redact`) and masked lines never suggested; 0600 file, written atomically; 30-day retention and 5,000-entry cap; the Rust side refuses to record while it is off; never sent anywhere |
| Saved tunnels (host names, ports, destinations) | `tunnels.toml` | 0600 file, written atomically; size-capped (512 KiB, 200 tunnels) and every field checked on load and on save; a file that fails to load is never written over; no secrets (a tunnel logs in the way its saved host does) |
| The builds people install | GitHub Releases | Pinned actions, no signing secrets in PR builds, SHA-256 sums, Sigstore provenance, SBOM |

## Who might attack, and how

1. **A malicious or compromised server** you connect to. It controls everything it sends: terminal output (escape sequences), SFTP listings (file names), file contents, host keys.
   - File names are checked to be a single path part (and on Windows, no drive letter or `:stream`) before anything is written locally.
   - Files opened "with the default app" that would run instead of open (`.bat`, `.exe`, `.desktop`, `.command`, …) are refused.
   - Terminal output is rendered by xterm.js, which does not run scripts or write the clipboard (no OSC 52).
2. **A malicious file you import**: an `ssh_config`, PuTTY/MobaXterm/Termius/CSV/Ansible export, or a pack.
   - Host names with whitespace, commas, `* ? ! | @ [ ] #` are refused, so "trust this host" cannot become "trust this key for every host".
   - `ProxyCommand` and other commands are never run, only noted.
   - Passwords in import files are never read.
   - Packs are data only: one-line snippets typed, never run; unknown fields refused.
   - Terminal colour schemes (`.itermcolors`, Windows Terminal JSON, Alacritty TOML, base16 YAML, kitty/Ghostty/Xresources) are parsed in Rust (`color_scheme_parse`, files up to 2 MB, at most 100 schemes): only colours are kept, each rewritten as `#rrggbb`, and names are stripped of control characters and cut to 60 characters. `settings.json` checks them again on load. Nothing else in the file is used.
3. **A web page whose text you copy.** Pasting several lines into a shell without bracketed paste would run them at once; the paste guard shows them and asks first.
4. **Another user on the same computer.** Config, vault, session and key files are 0600; edit folders are 0700 and not in shared `/tmp`.
5. **A workflow file someone gives you** (`workflows/*.toml`). It is a script by design: it runs the commands it lists on your hosts. Protections: nothing runs without **Run** and a confirmation that lists every command and host; commands only go to saved hosts over SSH (nothing runs locally, no `sh -c`); the file is size-capped and checked (ids, links, loops, sizes) before it is listed or run; the Rust side runs only what it reads back from disk, never a workflow sent by the window; runs never prompt, so they never accept a new or changed host key and take secrets only from the vault or ssh-agent; server output is stripped of escape sequences and shown as text.
6. **Someone reading your work memory** (`work-memory.json`): another user, a backup, a support bundle. It can show what you ran and where. Protections: off by default; 0600; secrets masked; retention and a cap; Forget and Delete everything. Suggestions never run anything: a workflow suggestion is rebuilt in Rust from the saved commands (the window sends only its id) and opens as an unsaved draft; snippets are one line and only typed.
7. **Code in the web view gone wrong** (an XSS bug in the UI). The CSP allows only Setu's own scripts. Rust commands check their inputs instead of trusting the UI: host-key trust needs a key the server offered, key commands only touch `~/.ssh`, JSON files are size-limited and parsed, workflow ids are checked so files stay in `workflows/`; `board_save` checks every card before writing `board.toml`; `memory_record` checks the session id and host name, caps the line and masks secrets itself; `prompt_detect` takes no input and only reports whether a few fixed files exist and whether shell start-up files (`~/.zshrc`, `~/.bashrc`, …, up to 512 KB each) contain the lines Powerlevel10k, Oh My Zsh, Starship or Oh My Posh add; it returns paths, never file contents, and runs nothing. Setu never installs or runs these prompt tools; Settings only shows lines to copy.
8. **A build of Setu with extensions** (docs/developer/extending.md). Extensions are Rust code compiled into that build by whoever made it; nothing is loaded at run time, and the open-source build has none. The hooks are given only what they need: audit events carry who, what, where and how it ended, never a password, passphrase, key or command output (login failures are a fixed reason, not the server's message); a command policy sees the command text of workflow steps so it can decide, and its refusal is recorded with the rule, not the command. A refused command never reaches the host. An access policy is asked before every SSH login (terminal or workflow) with the host's name, address, port, user and tags, never a secret; a refused login opens no connection. A session recorder (`with_recorder`) gets the bytes a server sends to an SSH terminal (the screen, which can show secrets the server prints) and its size changes, never the keystrokes, so passwords typed at a prompt that does not echo them are not recorded; the app writes a notice line into the terminal before the first byte is recorded, so nobody is recorded without being told. Local shells and workflow runs are never given to it. A build's settings page (`extension_panel`, `extension_action`) is plain data drawn as text (no HTML, no scripts); `extension_action` takes only a button id (at most 64 characters) and the extension decides what it means; files it saves go to a new file in Downloads, with the name reduced to `[A-Za-z0-9._-]`, never hidden, never over an existing file, 0600 and capped at 32 MiB. An address it asks to open in the browser must be `https://` or `http://` to this computer, without credentials or control characters, and at most 2048 bytes; other schemes (`file:`, custom handlers) are refused. The opener plugin is registered for Rust only: no capability lets the web view call it. The open-source build has no page, so both commands do nothing there.
9. **Other programs and computers that can reach a tunnel's port** (`setu-ssh::tunnel`). A local or SOCKS tunnel listens on a port on this computer, and anything that can connect to that port gets carried through your SSH login. The engine listens only where it is told; callers choose loopback (`127.0.0.1`) unless the person explicitly lets other computers on the network use it. The SOCKS proxy offers CONNECT only (no BIND, no UDP) and no password, so it must stay on loopback by default; destination names with spaces or control characters are refused before they reach the server, and a client that does not finish the handshake within 15 seconds is dropped. For remote tunnels, the server can open "forwarded" channels at any time: Setu accepts them only for ports this connection asked the server to listen on, and refuses every other one, so a server cannot make Setu connect to arbitrary local addresses. Agent forwarding and X11 forwarding are not requested. In the app, `tunnel_start` takes only an id and starts the tunnel as saved on disk; tunnels never prompt (host keys must already be trusted, secrets come from the vault or ssh-agent), the access policy of a build with extensions is asked before each connection, and an audit trail gets `tunnel.open` with the forward as OpenSSH writes it (`-L 5433:127.0.0.1:5432`), never traffic.
10. **Network tools used against you or by a server** (`setu-net`, `src-tauri/nettools.rs`). The tools send traffic on request: a port check, a DNS lookup, a ping run on a saved host, a Wake-on-LAN packet. Every host name is checked in Rust (`check_target`: name or address characters only, no leading `-`), so it cannot become an option or a second command in the fixed server commands (`getent ahosts NAME`, `ping -c 4 -W 2 NAME`). SSH hands those to the server's login shell, which is why names are limited to characters a shell treats as plain text. Their output is capped at 16 KiB and stripped to plain text. A port check through a host opens a `direct-tcpip` channel and closes it; nothing runs. Attempts are capped at 10 and timeouts at 5 seconds, so a check cannot become a flood. The TLS check accepts any certificate *for the handshake only*: verification against the system roots still runs, its result is reported to the person, and the connection is closed without sending a byte of application data, so an untrusted certificate is never used to carry anything. Signatures in the handshake are still checked. Certificates from the server are parsed with `x509-cert` (at most 8 per chain, texts cleaned of control characters and cut to 300 characters). Wake-on-LAN sends only to a broadcast address (255.255.255.255 or an IPv4 address ending in `.255`) on UDP port 9, so it cannot aim packets at an arbitrary host. Logins through a host never prompt and go through the access policy, like tunnels. Results are not saved or logged.
11. **A server that lies in its monitoring figures** (`setu-monitor`, `src-tauri/monitor.rs`). Monitoring runs one fixed, read-only command (`setu_monitor::COMMAND`) that takes no input, so nothing from the window or a host's settings reaches the server's shell. Its output is untrusted: only numbers are parsed (garbage is skipped, never trusted), used space is clamped to the total, disks, disk devices and interfaces are capped at 24 each, cores at 512, processes read at 8192 (and the process list is cut at 512 KiB on the server), output at 1 MiB a reading, and the texts kept (mount points, device, interface and process names) lose control characters and are cut to 120 or 64 characters before the window shows them as text. Only process ids, names, CPU ticks and memory pages are read from `/proc/<pid>/stat`, never command lines or environments, so arguments that hold secrets are not seen. A hostile server can at worst show wrong figures. Logins never prompt and go through the access policy; at most 24 monitors run at once, and none outlives its window. The hosts to watch when Setu opens are a list of saved host names in the window's local storage; each must still be in the inventory, and Rust looks it up again, so a stale or edited list can only start monitors on hosts the person already saved. Readings are not saved or logged. Desktop notifications for alerts are sent from Rust (`tauri-plugin-notification`); the window is given no notification permission, so a compromised page cannot post notifications. Their text holds the host's name, a figure and at most a cleaned mount point, with `<`, `>` and `&` removed so desktops that read markup in notifications show it as text. They hold no secrets and no command output.
12. **Server management run against you** (`setu-server`, `src-tauri/server.rs`). The Server view runs commands on a saved host, some of which change it (start, stop, restart, reload, enable, disable a systemd service). Protections: the window never sends command text; it names an action from a fixed list and a unit, and Rust builds the command. The only free input is the unit name, checked by `check_unit` against the characters systemd allows in unit names (no spaces, quotes, `$`, `;`, `|`, backticks, `/`, leading `-`), and quoted when it holds systemd's `\` escapes, so it cannot become a second command or an option. The line count for logs is clamped. Every change is shown to the person as the exact command (from `server_service_command`) and runs only after they agree; `server_service_action` rebuilds the same command from the same action and unit instead of trusting the window, asks the build's command policy, and records `server.change` (the command, never output). `sudo` is only ever run as `sudo -n`, so Setu never sends a password to it and a sudo prompt fails at once. Everything the server sends back (service names and descriptions, status, journal lines, error text) is untrusted: names are checked, texts lose escape sequences, control characters and bidirectional overrides and are cut (200 characters for descriptions, 512 KiB of logs, 16 KiB of change output, 4000 services), and the window shows them as text. Stopping or restarting the login, network or firewall service warns that access could be lost. Logins never prompt and go through the access policy, like tunnels and monitoring; kept connections close after 5 minutes unused. Nothing is saved or logged except the view's choices (host, sudo, log lines) in local storage.
13. **The supply chain**: a compromised dependency or GitHub Action. Lockfiles with `--locked`/`--frozen-lockfile`, `cargo deny` (advisories, licenses, sources), daily advisory audit, dependency review on PRs, actions pinned to commit SHAs, CodeQL, OpenSSF Scorecard.

## Out of scope

- An attacker who already runs code as you, or as root, on your computer (they can read your keychain and memory).
- Weaknesses of the server's own SSH setup.
- Physical access to an unlocked, logged-in computer while "unlock automatically" is on (the UI says so).

## Known gaps (tracked for later)

- SSH host certificates (`@cert-authority`) are refused rather than checked.
- Windows: `setu doctor` does not check file ACLs yet.
- Windows and macOS release signing switches on only once the certificates are added (see `docs/developer/releasing.md`).
- Signing secrets are repository secrets; moving them to a protected `release` environment that only `master` can use is a one-time settings change (see `docs/developer/releasing.md`).
